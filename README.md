# IntentLock
### Runtime Intent-Divergence Firewall for Autonomous Agent Payments
**Mastercard Innovation Challenge @ GFF 2026 — AI Defence Lab for Payment Security**
**Track: Red Team / Blue Team Adversarial AI System**

> Declared intent is not necessarily the same as executed intent. IntentLock continuously compares the two.

---

## 1. The Problem

Payment networks have built real, working infrastructure to verify that an AI shopping agent is *who it claims to be* and *authorized to transact* — Mastercard Agent Pay (MDES Agentic Tokens), Mastercard Verifiable Intent (co-developed with Google, announced March 2026), Visa's Trusted Agent Protocol, and Google's AP2. These establish agent identity, spend caps, merchant scope, and a tamper-resistant record of what the user authorized.

What none of them do is continuously verify, in real time, whether the agent's *actual observed behavior* still matches that authorized intent while it's happening. An agent can stay strictly inside its authorized spend cap and merchant scope while still being manipulated into buying something the user never meant to buy. To existing authorization checks, that transaction looks completely fine.

**IntentLock is a runtime behavioral security layer that observes an agent's live execution trajectory and scores whether it still aligns with the user's declared intent — before the payment settles.** It is a complement to existing trust infrastructure, not a replacement for it.

---

## 2. Positioning — what this is and isn't

IntentLock does **not** claim to replace or outperform Mastercard Agent Pay, Verifiable Intent, Visa's Trusted Agent Protocol, or Google AP2. Those systems answer *"is this agent authorized to act?"* IntentLock investigates a narrower, complementary question: *"does the agent's observed execution still correspond to what was authorized?"*

This prototype does not connect to, call, or attempt to reproduce any real Mastercard, Visa, or Google production system. Every attack, storefront, merchant, and transaction in this repository is synthetic and runs entirely inside a mock environment built for this project. No real cardholder data, PII, or production payment data is used anywhere.

## 3. Architecture

```
        Mastercard Agent Pay / MDES Token
        (identity, spend cap, scope)
                    │  session telemetry
                    ▼
   ┌─────────────────────────────────────────┐
   │              BACKEND (Python)            │
   │  ┌───────────────┐  ┌──────────────────┐ │
   │  │   RED TEAM    │─▶│    BLUE TEAM     │ │
   │  │ mock shopping │  │ 8 features →     │ │
   │  │ agent+attacks │  │ LightGBM scorer  │ │
   │  └───────────────┘  └────────┬─────────┘ │
   │       (Flask API: /simulate, /score)      │
   └──────────────────────────────┼───────────┘
                                  │ risk score + reason codes
                                  ▼
   ┌─────────────────────────────────────────┐
   │          FRONTEND (Streamlit)            │
   │  Session trace pane │ Verdict pane       │
   └─────────────────────┬───────────────────┘
                         │ verdict
                         ▼
              Allow · Verify · Block
```

Data flows one way: the red team generates a labeled synthetic dataset offline → the blue team trains once on it → at runtime, a session goes through the same feature extractor → the trained model scores it → the frontend renders the verdict.

## 4. Attack Taxonomy — 4 families, ~20 variants, one detection target

All variants resolve to the same underlying failure: the agent's observed behavior diverges from the user's declared intent. One coherent detector, not four disconnected ones.

| Family | Variants |
|---|---|
| **F1 — Agent Manipulation** (prompt injection) | gift_card, warranty, subscription, fake_discount, context_poisoning, no_effect (injection resisted — clean label) |
| **F2 — Merchant Manipulation** (counterfeit storefronts) | counterfeit_storefront, merchant_substitution, seller_hijacking, redirect, metadata_poisoning |
| **F3 — Intent / Decision Drift** (no injection) | unauthorized_upgrade, quantity_change, unrequested_addon, specification_change, subscription, stale_intent |
| **F4 — Transaction State Integrity** (TOCTOU) | cart_mutation, price_mutation, quantity_mutation, checkout_state_mismatch |

Plus two non-fraud categories: **clean** sessions (realistic internal variation) and **benign_substitution** sessions (legitimate swaps — out-of-stock, better-rated alternatives — labeled not-fraud to keep FPR honest).

## 5. Dataset

`backend/data/agentic_fraud_telemetry.parquet` — 9,200 synthetic sessions, generated by `backend/redteam/batch_generator.py`.

| Family | Count | Fraud? |
|---|---|---|
| clean | 3,800 | No |
| benign_substitution | 2,000 | No |
| f1_prompt_injection | 1,100 | Yes (except no_effect variant) |
| f2_counterfeit_storefront | 850 | Yes |
| f3_intent_drift | 850 | Yes |
| f4_toctou_protocol | 600 | Yes |

**Split: 65% legitimate / 35% fraud.** Substitutions are scoped to the same item type as the user's intent (a keyboard session only gets keyboard alternatives) — this is critical for keeping benign FPR honest.

Each row contains: stated intent (natural language), structured intent (category, budget, quantity), spend cap, authorized category, execution steps, cart, injected text encountered, TOCTOU flag, domain mismatch flag, attack family, attack variant, and fraud label.

## 6. Detection — 8 features

| Feature | What it measures |
|---|---|
| `intent_divergence` | Cosine distance between intent embedding and cart embedding |
| `high_risk_sku_ratio` | Fraction of cart value that is vouchers, addons, or subscriptions |
| `spend_cap_proximity` | Total cart value ÷ authorized spend cap |
| `graph_entropy` | Shannon entropy over tool-call transition pairs |
| `protocol_consistency` | TOCTOU tamper flag |
| `injection_density` | Normalized count of command-syntax keywords in injected text |
| `merchant_scope_delta` | Domain mismatch flag |
| `structured_intent_mismatch` | Count of non-physical items in cart, normalized |

**Model:** LightGBM gradient-boosted trees, trained on 80% of the dataset, evaluated on 20%.

**Key results** (full details in `docs/eval_report.md`):
- ROC-AUC: 1.0 on synthetic data (*note: partly free — see eval report caveats*)
- FPR on clean sessions: 0.0%
- FPR on benign_substitution: 0.0%
- Unseen-variant generalization: 100% detection on `subscription` and `seller_hijacking` held out entirely from training

**Output:** 0–100 risk score → Allow (0–29) / Verify (30–69) / Block (70–100) + top reason codes ranked by value × model feature importance, baseline-adjusted so ubiquitous features don't dominate the display.

## 8. Setup & Reproduction

```bash
# 1. Clone and create environment
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # Mac/Linux

pip install -r requirements.txt
```

**Step 1 — Generate the dataset:**
```bash
python -m backend.redteam.batch_generator
```
Prints family and variant counts, writes `backend/data/agentic_fraud_telemetry.parquet`.

**Step 2 — Train the classifier:**
```bash
python -m backend.blueteam.train_classifier
```
Prints ROC-AUC, per-family detection rates, and FPR on clean/benign sessions separately. Saves `models/intentguard_lgbm.pkl`.

**Step 3 — Start the API:**
```bash
python -m backend.api.server
```
Runs on `http://localhost:5000`. Endpoints: `GET /health`, `POST /simulate`, `POST /score`.

**Step 4 — Run the demo:**
```bash
# Windows (using venv Python directly)
python -m streamlit run frontend/streamlit_app/app.py --server.headless true

# Mac/Linux
streamlit run frontend/streamlit_app/app.py
```
Open `http://localhost:8501`. Select any of the 6 scenarios and click **Simulate & Score**.

> Both the API server (Step 3) and the Streamlit app (Step 4) must be running at the same time for the demo to work.

## 9. Key design decisions

**Flask over FastAPI:** two endpoints, synchronous, internally consumed — no async or auto-doc benefit worth the extra complexity.

**Streamlit over Next.js:** delivers a real two-pane live dashboard without a separate build pipeline. Backend/frontend split is kept clean so the same two API endpoints could serve a different frontend later.

**Benign_substitution category:** explicitly included and labeled not-fraud. Without it, a model can achieve near-zero FPR trivially because the only non-fraud examples are perfectly clean sessions. Benign substitutions are the honest test — legitimate deviations that look superficially like drift.

**Per-intent substitution scoping:** substitution candidates are attached directly to each base intent (a keyboard request only gets keyboard alternatives). Cross-category substitutions caused `intent_divergence` to spike to ~0.9 on benign rows, which would have produced ~94% FPR. The fix was a data quality change, not a model change.

**Reason ranking:** top reasons are ranked by `excess_above_baseline × feature_importance`, not raw feature value. Raw value caused ubiquitous features like `spend_cap_proximity` to dominate every verdict regardless of whether it was the actual discriminating signal.

## 10. Limitations

- Dataset is fully synthetic; results demonstrate performance on this benchmark, not real-world fraud-detection performance.
- Does not connect to any real payment rail, processor, or card network.
- `injection_density` uses a keyword regex — a deliberately evasive payload avoiding those words would score 0.
- Allow/Verify/Block thresholds are illustrative and would need calibration against real production distributions.
- "Verify" and "Block" are simulated — no real step-up authentication or token revocation occurs.
- F3 (intent drift) is expected to be the hardest family on real or noisier data — it has no binary anchor feature, relying entirely on continuous semantic and spend signals.
